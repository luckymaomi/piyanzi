# 迎审检查单：人翻手册 → 一句话交代皮燕子

---

## 这活是什么

迎审要填检查单「符合性声明」：每条检查项对照手册条款，按原文写入；要佐证再抽 PDF。

---

## 以前人怎么干

1. 看检查单这一行要什么。  
2. 打开手册 PDF，搜索或翻目录。  
3. 读上下文，判断是不是同一回事。  
4. 选定后，把该条款全文誊进表（常要求一字不差）。  
5. 下一条，窗口还在 PDF 和 Excel 之间切。  

一条常常十几分钟到几十分钟。约 29 条，按每条半小时左右估，人要 **14～15 小时** 很正常。

---

## 现在实际怎么干（按 Skill 落地时的操作）

人把检查单、手册路径用一句话或几轮交代清楚（哪几行、哪几本、预检还是实写）。  
Agent 打开「检查单手册比对填写」后，对每一条大致做下面这些事——下面按**真实会调用的工具**写，不按想象写。

### 1. 读检查单行

用脚本或读表把这一行的检查项名称、要素、提示拿出来，拆成对象 / 动作 / 条件，得到要搜的词。  
人不需要自己把词写进检索框。

### 2. 手册必须是「可读文本」

`.md` / `.txt` 直接搜。  
`.docx` 先 Shell + Python（如 python-docx）抽成临时文本，再搜；不对着 Word 二进制瞎 Grep。  
扫描 PDF 转不成文本的，这条手册先跳过或等人转好。

人还在 PDF 里肉眼翻的时候，机器已经在纯文本上工作。文本化本身就去掉翻页和渲染。

### 3. 定位：Grep 扫全文，不是一页页看

粗读：对手册目录或已抽文本跑 Grep（核心词，限制命中条数），看哪些文件、哪些行附近有关。  
同一回合里常常**并行**丢多个工具，例如：Glob 看有哪些手册文件 + 对目录 Grep 宽词；有时多本、多词一起发，等一轮结果回来再往下收。

精读：缩到粗读点名的那一个文件，再用更窄的词或条款号片段 Grep（带前后几行），或按行号短 Read，确认是不是该要的那一款。

读周边：Grep 给出行号后，Read 指定 offset / limit，把该条款从本条编号读到下一条同级编号之前（含子项），得到候选全文。

和人的差别在这里最实在：

- 人：一次盯一个窗口，滚动条往下拖，搜错词就重来。  
- 机器：Grep 对整份文本一次扫完；Read 按行号跳转，不经过「翻到第几页」。  
- 并行只省「等工具」的来回，真正大头是 **全文检索 + 按行跳转**，不是人眼扫 PDF。

### 4. 语义比对（两轮）

候选段落已经进对话上下文后，和检查项的对象 / 动作 / 条件对：

1. 对不上的丢掉。  
2. 再复核：多条都能对时只留最贴的。  

对不上就留空，不硬写。  
这一步仍是判断，但判断对象是「已经搜出来的几段字」，不是整本手册。

### 5. 写入

预检：拟写入文案给人看。  
实写：先备份检查单，再用脚本改符合性声明列；写完按手册原文再对字。

佐证：解析声明里的《手册》+ 条款号，在 PDF 里定位正文页，抽命中页±1，加高亮，按交代的目录落下——也是脚本批量，不是另存为点二十九次。

---

## 为什么约 29 条大约 11 分钟就跑完

实测墙钟：约 **29 条 / 约 11 分钟**（约 20～25 秒/条）。

快，主要因为：

1. **搜的是文本索引式 Grep**，不是 PDF 翻页。  
2. **定位靠行号 Read**，打开即是目标段。  
3. **一轮里可并行多个 Grep / Glob / Read**，少等几轮来回。  
4. **比对只面对候选段**，不在整本里反复找。  
5. **写入和抽页用脚本**，不手工粘贴、不手工另存。

人的 14～15 小时里，大部分花在「找」和「切窗口」；机器把「找」换成检索和跳转，「写」换成批处理。  
语义比对省不掉，但已经不再占主时间。

这不是固定规则批量替换单元格；每条仍要拆题、检索、比对、对不上留空。人侧是一句话交代和事后抽查，不是自己再翻二十九遍书。
